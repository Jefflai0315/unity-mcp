## Big Picture: Two Sibling Products from Coplay

| | [coplay-unity-plugin](https://github.com/CoplayDev/coplay-unity-plugin) | [unity-mcp](https://github.com/CoplayDev/unity-mcp) |
|---|---|---|
| **What it is** | Premium in-Editor AI chat assistant | Open-source MCP bridge (MIT) |
| **UI** | Built-in chat window (`Cmd+G`) | No chat UI — uses Cursor, Claude, VS Code, etc. |
| **Source** | Closed-source DLL (~19 MB) | Fully open (C# + Python) |
| **Backend** | Coplay cloud (auth, billing, LLM routing) | Self-hosted Python FastMCP server |
| **MCP role** | MCP **client** — connects to external MCP servers | MCP **server** — exposes Unity tools to LLMs |

They are **not the same codebase**. Coplay is a full product; unity-mcp is a protocol bridge. You *can* wire them together by adding unity-mcp as an MCP server inside Coplay's config.

## 2. How to Cache and Maintain Chat History Efficiently

### unity-mcp: **no chat history** (by design)

MCP is request/response. **Conversation history lives entirely in the MCP client** (Cursor thread, Claude chat, etc.). The server only caches routing/session state:

| Cache | Location | Purpose |
|-------|----------|---------|
| Active Unity instance per session | `unity_instance_middleware.py` `_active_by_key` | Route tools to correct Editor |
| Plugin WebSocket sessions | `plugin_hub.py` | Map session ↔ Unity project |
| Editor state snapshot | `EditorStateCache.cs` (~1s tick) | Fast `mcpforunity://editor/state` reads |
| API key validation | `api_key_service.py` | 300s TTL for remote auth |
| Tool visibility metadata | Middleware | Filter `tools/list` per project |

Session key derivation:

```71:89:/Users/jefflai/COplay-learn/unity-mcp/Server/src/transport/unity_instance_middleware.py
    async def get_session_key(self, ctx) -> str:
        """
        Prioritizes client_id for stability.
        In remote-hosted mode, falls back to user_id for session isolation.
        Otherwise falls back to 'global' (assuming single-user local mode).
        """
        client_id = getattr(ctx, "client_id", None)
        if isinstance(client_id, str) and client_id:
            return client_id
        user_id = await ctx.get_state("user_id")
        if isinstance(user_id, str) and user_id:
            return f"user:{user_id}"
        return "global"
```

**Token efficiency patterns** (not memory, but context management):

- Read **resources** before mutating (cheaper than tool calls)
- Use **paging** (`page_size`, `cursor`) on large hierarchies
- Use **`batch_execute`** (up to 25 commands per batch) instead of sequential calls
- Enable only needed **tool groups** to reduce token load

The only "history" feature is `execute_code` with `get_history` / `replay` — a log of C# executions in Unity, not chat.

### coplay-unity-plugin: **hybrid local + cloud** chat history

This is where real chat persistence lives:

```
User message
  → Local save (ChatHistoryRepository)
  → Stream to Coplay cloud (StreamSendMessageToLLM)
  → Stream response back to UI
  → Atomic local save (ChatThreads.SaveStateAtomically)
  → Sync threads/messages with backend (GetThreads, GetThreadMessages)
```

**Key classes** (from DLL decompilation via `monodis`):

| Component | Role |
|-----------|------|
| `ChatThreads` | Thread CRUD, `LoadState`, `SaveStateAtomically`, corruption recovery |
| `ChatHistoryRepository` | Local message persistence |
| `ChatHistory` | Message model |
| `TextFormattingCacheService` | Caches rendered message text (`CacheExpirationDays`, `CacheStalenessSeconds`) |
| `ChatScrollPositionModel` | Per-thread scroll position |
| `ChatInputHistory` | Input field history (grouped by interval) |
| `CheckpointGitService` | Git snapshots before changes |
| `CheckpointHashSyncService` | Sync checkpoint hashes with backend |

**Local storage paths** (runtime-composed):

- `ChatThreadsPath`, `MessageHistoryPath`, `AssistantStatePath`
- `FormattingCachePath`, `CoplayCheckpointPath`, `OrchestratorSessionPath`
- `McpServersFilePath`, `CustomRulesFilePath`, `PipelineRecordingsPath`

**Context caching** (separate from chat):

- `SyncContext` + `GetContextHash` — hash-based invalidation so unchanged project context isn't re-sent
- `ContextSyncController` — syncs selected providers before each request

**Design takeaway:** Coplay keeps messages locally for fast UI, syncs to cloud for cross-device/backup, caches formatted rendering, and uses content hashes to avoid redundant context uploads.

## 5. How MCP Comes Into Place

### In unity-mcp: MCP is the **entire architecture**

```
MCP Client (Cursor)
    ↕ MCP Protocol (stdio or HTTP /mcp)
Python FastMCP Server
    ↕ WebSocket /hub/plugin
Unity MCPForUnity Plugin
    ↕ CommandRegistry (reflection)
Unity Editor APIs
```

1. Client connects → MCP `initialize`
2. Client calls `tools/list` + `resources/list`
3. Client reads `mcpforunity://editor/state` (optional)
4. Client calls `tools/call` → Python routes → Unity executes → JSON result
5. Client owns all chat history and orchestration

**Tool groups** save tokens — only `core` (30 tools) enabled by default; enable `testing`, `vfx`, `docs`, etc. via `manage_tools`.

---

### In coplay-unity-plugin: MCP is an **optional extension**

Coplay embeds `ModelContextProtocol.Core` v0.2.0 as an **MCP client**:

| Class | Role |
|-------|------|
| `MCPHost` | Loads servers from `McpServersFilePath`, registers stdio/SSE clients |
| `MCPClient` | JSON-RPC to external MCP servers |
| `MCPFunctions.InvokeMcpTool` | Exposed as an assistant tool |
| `MCPToolFunctions` | `ExecuteScript`, `GetUnityEditorState`, etc. |

**Two tool layers:**

1. **Native `CoplayTools`** — built into the DLL (scene, files, 3D gen, etc.)
2. **External MCP tools** — via `InvokeMcpTool` (can wrap unity-mcp or any MCP server)

`PromptBuilder` takes `MCPHost` in its constructor — external MCP tools and prompts are folded into context sent to the LLM.

**Practical connection:** Configure unity-mcp in Coplay's MCP servers file → Coplay's chat can call unity-mcp's 43 tools alongside its native tools. Overlap exists (both can manage scenes/scripts), but they serve different primary use cases.
